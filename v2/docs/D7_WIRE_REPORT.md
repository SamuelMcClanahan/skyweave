# D7 wire freeze report

**Labels.** Datagram sizes, the worst-case budget, the parity table and
the Tier IV verdicts are recomputed deterministically on every run of
this generator. Host-loopback timing is **Measured** and is read from
`docs/d7_evidence.json`, recorded by the `measure` subcommand.
Everything carried in from earlier phases keeps the label it had.

**Loopback latency is not network latency.** Every timing number below
crosses `127.0.0.1` inside one host: no NIC, no switch, no cable, no
contention. D9 measures the real switch; nothing here predicts it.

Seed 7. Tier IV magnitudes read from `configs/d6_faults.yaml`
(frozen, never restated in code). Generated by
`uv run python -m skyweave2.transport.report generate` — byte-identical
for identical inputs, seed and evidence file, cross-process.

## Worst case the SCHEMA allows

The measured distribution above is a property of one clean clip. The
ceiling has to hold for the worst case the declared bounds PERMIT:
every string at its nanopb `max_size`, every varint at its widest
encoding, a negative `capture_ts_ns`, and every optional field present.

| Component | Bytes |
| --- | --- |
| Header | 4 |
| FrameEnvelope (36-char UUID, two 64-char revisions) | 247 |
| Each Observation2D (64-char evidence_ref, widest varints) | 163 |
| Declared observation bound | 5 |
| Worst-case datagram | 1074 |
| Headroom | 126 |

**The 1200 B ceiling admits at most 5 observations per
capture event** at the declared bounds. That number is derived by
encoding, not estimated, and `proto/skyweave.options` declares exactly
it, so the D8 nanopb daemon allocates the same bound this host enforces.

Observations altered by the round trip: 0 of 838.

D0's type column declares `time_sync_error_ms`, `exposure_us`,
`gain_db`, `line_readout_us` and `confidence` as `float`, i.e. IEEE-754
binary32, while the pydantic models hold doubles. The `.proto` follows

every other timestamp are `double`/integer and cross the wire exactly —
no geometry input is touched.

## Findings

### D7-F1 — the ceiling admits few observations per capture event

At the declared bounds the worst-case datagram is 414 B for ONE observation and
1074 B for 5; the ceiling
permits at most 5. The gate clip never exceeds
1 observation(s) per event, so nothing is blocked
today, but the D4 detector has NO per-frame component cap
(`DetectorConfig` bounds component area, not component count).

Consequence if shipped: a cluttered frame — birds, insects, rain —
produces more than 5 components and the capture event
becomes unsendable. It fails loudly (`TooManyObservations`), which is
correct behaviour and much better than a truncated packet, but it is
still a lost measurement. Three levers exist and all three are
planning-session decisions, not code changes: raise the ceiling toward
the path MTU (~1472 B on untagged Ethernet), shorten the
`evidence_ref`/revision bounds, or allow a capture event to span
datagrams — which the current freeze forbids outright.

### D7-F2 — D0 declares binary32 for five envelope/observation fields

`time_sync_error_ms`, `exposure_us`, `gain_db`, `line_readout_us` and
`confidence` are `float` in D0's type column, so the wire cannot
represent an arbitrary double exactly. On this clip the effect is
0 altered observation(s) and the acceptance table is
unchanged, because the only one of those fields the fusion chain reads
is `time_sync_error_ms`, and it feeds the systematic bound (report-only,
never the filter) which is zero under the frozen default
`FusionConfig.systematic`.

Consequence if shipped: once `SystematicConfig.estimated_speed_mps` is
non-zero — which D6.1 requires for an honest clock bound — the declared
bound is computed from a value that changed by up to ~6e-8 relative on
the wire. That is far below any decision boundary, but it means
`decode(encode(x)) == x` is FALSE for the envelope and any future test
asserting exact envelope round-trip will fail for this reason and not a
real one. Widening the field would be a D0 contract change and is not
this phase's call.

### D7-F3 — unpaced replay is single-source only

DETERMINISTIC pacing carries synthetic capture times and never sleeps.
Across three independent processes that is not a valid multi-camera
mode: one node can transmit its entire clip before another starts, so
the aligner sees the trailing cameras' capture times far behind the
newest and correctly rejects them as LATE. The engine is right and the
mode is wrong.

The rig therefore uses WALL_CLOCK pacing with a SHARED epoch across all
three edges — which is what PTP-disciplined boards give you for free in
D8/D9, and what a per-process start time silently does not. Pinned as a
test (`test_unpaced_multiprocess_replay_is_not_a_valid_multi_camera_mode`)
so the constraint cannot be forgotten.

### D7-F4 — accelerated replay is bounded by the lateness window

Replaying faster than 1x is not free. At speed S a D-millisecond
scheduling hiccup on the host reads as D*S milliseconds of CAPTURE-TIME
lag to the aligner, because the capture timestamps still carry their
original 1x spacing. The aligner's window is
`AlignerConfig.lateness_ns` = 100 ms, so the safe speed is
`lateness_ms / (worst host jitter * safety factor)`.

This was found the way findings should be found: the rig test failed
at speed 10 on a LOADED host with three observations excluded as
`late`, and the failure read as a socket-vs-file parity break when the
wire had done nothing wrong.

With the declared jitter budget and a
10x factor covering
the observed max-to-p95 ratio, the bound comes out at 1x, so
`TransportConfig.rig_replay_speed` is 1.0 — the rig replays at REAL
TIME. `test_the_rig_replay_speed_leaves_room_for_host_jitter` re-derives
it from `AlignerConfig.lateness_ns`, so the two cannot drift apart: when
the jitter budget was widened after a loaded-host measurement, that test
failed and forced the speed down rather than letting an accelerated rig
keep a margin it no longer had.

Consequence if shipped: none for the deployed system — 1x IS the
deployment. The consequence is for whoever next accelerates a replay to
save test time and reads the resulting lateness as a transport defect.

### D7-F5 — a receive buffer sized at the ceiling truncates silently

`recv(1200)` on an oversized datagram returns 1200 bytes with no error
and no flag; the tail is gone and what remains often still parses. The
receiver therefore reads into a 65535 B buffer and REJECTS anything over
the ceiling. Demonstrated on this platform rather than assumed:
`test_a_ceiling_sized_receive_buffer_really_would_truncate` proves the
trap is real before the guard is shown to close it.

## Adversarial review before hand-back

Five lenses (silent truncation, encode/decode asymmetry, adapter
divergence under faults, tests that cannot fail, scope and frozen
paths), each finding independently verified by a second pass whose job
was to REFUTE it. 23 candidate findings, 17 refuted, 6 confirmed and
fixed before hand-back. The confirmed six, because what a review caught
is more useful to the next phase than a claim that it found nothing:

| # | Found | Fix |
| --- | --- | --- |
| 1 | 8 of 13 nanopb bounds were enforced on the measurement plane only; health, evidence and control had none. The `.options`-vs-`WireLimits` guard was structurally blind to them — a mangled file passed W2. | `declared_limits_from_options` now rejects any bound nothing enforces, so an unenforced line cannot be added; all four planes check. |
| 2 | A `float` field beyond FLT_MAX SATURATED to infinity instead of narrowing: a finite measurement silently becoming `inf`. | `_check_float32` rejects it loudly; a sender's explicit infinity is still carried. |
| 3 | `line_readout_us` was 0.0 in every fixture, and 0.0 is proto3's implicit default — deleting the encoder line left the suite green. | A non-zero rolling-shutter case pins field 15. |
| 4 | W6 compared packet-age and transit MEDIANS, so dropping the due-time bookkeeping and joining against send time still passed. | Exact per-receipt identity: age minus transit IS the scheduling error. |
| 5 | `test_options_parser_can_fail` only proved a bad file raises; `return WireLimits()` — ignoring the file entirely — survived. | A positive-propagation test on a shifted copy of the real file. |
| 6 | Nothing tied `adapter.stats.sizes` to real datagram lengths; recording a constant 1 left the suite green. | Cross-checked against the independent encoder. |

Findings 3-6 are test-strength defects: the code was right, the tests
could not have caught it being wrong. Findings 1 and 2 were real
encode-path gaps, and finding 1 contradicted a claim this codebase made
about itself in three places.
